# دليل البناء الآمن للتطبيقات الثلاثة (Google Play Protect)

**الحالة:** تم تجهيز إعدادات GitHub لإنتاج APK بصيغة Release موقّع فقط. لم يتم إنشاء APK نهائي أو فحصه ضد Google Play Protect، لأن مفاتيح التوقيع يجب أن تظل تحت سيطرتك.

## أولاً — قبل رفع الملفات
1. خذ نسخة احتياطية من بيانات المحاسبة من داخل التطبيق الحالي وتأكد من إمكانية استعادتها.
2. **لا تحذف التطبيق المثبّت** قبل التأكد من تطابق شهادة توقيع الإصدار الجديد معه.
3. حافظ على نفس applicationId وأرقام الإصدار الموجودة؛ لم نغيّرها في هذه التعديلات.
4. لا تضع ملف `.jks` أو كلمة مرور أو نص BASE64 في GitHub العام أو في الدردشة. خزّنها في Secrets.

## ثانياً — رفع ملفات التحديث
- إن كان مستودعك يحتوي على المشروع الكامل بالفعل: فك ملف `UPDATE...zip` الموافق له، وارفع الملفات داخله إلى **نفس المسارات** في المستودع، بما فيها مجلد `.github` المخفي.
- إن أردت بدء مستودع نظيف: ارفع **محتويات** حزمة `FULL_PROJECT...zip`، لا ملف ZIP نفسه.
- مشروع الرئيسي والمندوب ضمن مستودع واحد ويحتوي على `app` و`field_agent`.
- مشروع Solo مستقل ويحتوي فقط على `app`.

## ثالثاً — إعداد أسرار التوقيع عبر GitHub
افتح المستودع > Settings > Secrets and variables > Actions > New repository secret.

للمشروع الرئيسي والمندوب، يجب وجود هذه **الأسماء الأربع** (قيمها من *المفتاح الأصلي المستعمل في النسخ الحالية*):
- `TA_KEYSTORE_BASE64` : محتويات ملف keystore بعد تحويله إلى Base64 دون سطور إضافية.
- `TA_STORE_PASSWORD` : كلمة مرور مخزن المفاتيح.
- `TA_KEY_ALIAS` : اسم المفتاح داخل المخزن.
- `TA_KEY_PASSWORD` : كلمة مرور المفتاح.

لمشروع Solo المستقل، يجب وجود:
- `SOLO_KEYSTORE_BASE64`
- `SOLO_STORE_PASSWORD`
- `SOLO_KEY_ALIAS`
- `SOLO_KEY_PASSWORD`

**مهم:** إذا كان التوقيع الحالي مختلفاً عن المفتاح الذي ستستخدمه، فلن يعمل التحديث فوق التثبيت الحالي. يجب الاستعادة من نسخة احتياطية بعد التحقق، ولا تحذف البيانات تلقائياً.

## رابعاً — التشغيل
في GitHub افتح **Actions** ثم اختر:
- `Tiqany Acc - Main Signed Release` لإصدار الرئيسي.
- `Tiqany Acc - Agent Signed Release` لإصدار المندوب.
- `Tiqany Acc - Solo Signed Release` لإصدار النسخة المستقلة (في مستودع Solo).
اضغط `Run workflow`، ثم افتح آخر تشغيل ناجح وانزل إلى `Artifacts` للحصول على APK وملف SHA-256.

لن تُنتج هذه المسارات APK تجريبياً عند نقص مفاتيح التوقيع؛ ستتوقف برسالة واضحة بدلاً من ذلك.

## اختيار إضافي — تثبيت بصمة توقيع ثابتة
يمكنك في Settings > Secrets and variables > Actions > Variables إضافة متغير `TA_EXPECTED_CERT_SHA256` للمشروع الرئيسي/المندوب، و`SOLO_EXPECTED_CERT_SHA256` لمشروع Solo، وتضع بصمة SHA-256 لشهادة التوقيع الأصلية (64 خانة hex). إذا غيّر أحدهم مفتاح التوقيع دون قصد يتوقف البناء، بدلاً من إنتاج تحديث غير متوافق.

## خامساً — فحص Play Protect
- جرّب APK الجديد على جهاز اختبار غير حامل لبيانات محاسبية مهمة مع Play Protect مفعّل.
- احتفظ بلقطة كاملة لرسالة التحذير ونسخة APK المُبلّغ عنها، ولا تتجاوز التحذير قبل التحقق من سببه.
- فحص التوقيع والتحقق من الصلاحيات لا يضمنان قبول Play Protect. إذا استمر تصنيف «ضار» بعد فحص الأمان، قدّم طلب مراجعة رسمي إلى Google.
- لا ترفع APK خاصاً يحتوي على بيانات أو مفاتيح إلى خدمات فحص عامة بلا مراجعة سياسة الخصوصية.

## ماذا تغيّر؟
- بناء Release موقّع إلزامياً للمشاريع الثلاثة.
- التوقف بدلاً من إصدار Debug عند نقص Secrets.
- التحقق من صحة توقيع APK وطباعـة بصمة شهادته وإنشاء SHA-256.
- فحص مبدئي للصلاحيات وهوية الحزمة ومنع cleartext وسلامة ملفات المشروع قبل إصدار النسخة.
- ملف `.gitignore` يمنع إضافة ملفات المفاتيح الخاصة بطريق الخطأ.
- لم يتم تعديل منطق المحاسبة أو واجهات التطبيق أو رقم الحزمة أو الإصدار.
